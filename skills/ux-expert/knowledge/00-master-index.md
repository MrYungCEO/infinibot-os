## Categories
- **hierarchy** — visual weight, focal points, scanning paths
- **typography** — type scale, line-height, measure, pairing
- **color** — palette roles, contrast, semantic color
- **spacing** — 4/8pt grids, vertical rhythm, density
- **motion** — duration, easing, choreography, reduced-motion
- **forms** — labels, validation, autofill, error recovery
- **conversion** — CTAs, social proof, friction, value props
- **accessibility** — WCAG 2.2 AA, ARIA APG, keyboard, screen reader
- **states** — empty / loading / error / success / partial
- **navigation** — IA, breadcrumbs, search, wayfinding
- **dock** — floating panels, command palettes, persistent toolbars
- **microcopy** — labels, errors, empty states, button verbs
- **density** — progressive disclosure, summarize-then-detail
- **responsive** — mobile-first, breakpoints, touch targets
- **feedback** — toasts, status, optimistic UI, undo
- **brand** — token reuse, theming, consistency

## How to use during an audit
1. For each screenshot, walk the 16 categories.
2. For each detected issue, link the finding to the file + pattern it violates.
3. The methodology doc (`methodology/audit-process.md`) defines severity + scoring.

## Pattern entry structure
Every pattern entry uses:
- **Pattern** — name + one-line definition
- **When to apply** — surface / context triggers
- **How to apply** — concrete, atomic steps (3–6 bullets)
- **Source(s)** — author/org + year
- **Anti-patterns** — what failure looks like
